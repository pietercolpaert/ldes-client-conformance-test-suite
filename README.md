# LDES 1.0 Client Conformance Test Suite

This repository is the home of a black-box conformance test suite for clients of
the [Linked Data Event Streams (LDES) 1.0 specification][ldes-1.0]. It turns the
consumer requirements in the specification into reproducible HTTP scenarios,
observable client outcomes, and machine-readable
[EARL 1.0][earl] reports.

The project has an executable suite of 114 deterministic scenarios. Against the
reference adapter they behaviorally verify 77 of the 100 reviewed LDES 1.0
requirements; a further requirement is mapped but not verified, because the
optional TREE Profile fixtures are inapplicable to an adapter that does not
declare that capability. The remaining 21 requirements have an explicit
boundary, optionality, manual, or deferred rationale. CI rejects an applicable
client `MUST` or `SHOULD` that has neither a test mapping nor a rationale.

A mapping is not evidence. `reports/<adapter>/coverage.json` therefore reports
`verified` (a mapped test actually passed), `mapped` (a mapping exists but no
mapped test passed), and rationales counted separately per classification. It
also flags requirements whose only evidence comes from fixtures declaring a
weaker level than the requirement itself. Rationale counts are never added to
coverage counts. The numbers above are generated by `npm test`; do not edit
them by hand.

## Goals

- Trace every test to an exact normative statement in LDES 1.0.
- Test externally observable behavior rather than implementation details.
- Exercise any client through a small, language-neutral adapter contract.
- Cover the LDES 1.0 algorithms as separately reportable compliance groups:
  unordered traversal, ordered traversal, member extraction, and context
  information.
- Distinguish required behavior, recommended behavior, optional capabilities,
  and requirements that only apply to a supported mode.
- Produce one EARL assertion per test case and test subject.
- Make failures reproducible from fixtures, request logs, client events, and
  client revisions.

Non-goals for the first release are server conformance, performance
benchmarking, and testing client extensions that are not needed by LDES 1.0.
Extension tests may be added later, but will never affect an LDES 1.0
conformance claim.

## Compliance groups

LDES 1.0 is easier to test as a set of algorithm claims rather than one large
pass/fail label. The suite therefore reports these groups independently:

| Group | Scope | Dependency |
| --- | --- | --- |
| Unordered traversal | Entry-point discovery, synchronization runs, state, deduplication, HTTP behavior, retry/error handling, unordered relation traversal, rebalancing resilience, immutable node handling, cache headers, ETags, and polling interval behavior | None |
| Ordered traversal | Ordered ascending traversal, SHACL property path evaluation, ordering prerequisites, relation-bound interpretation, queue prioritization, and transaction-finalizing members | Independent mode claim |
| Member extraction | The LDES member extraction algorithm, including default-graph subject stars, named graphs whose graph IRI is the member IRI, recursive blank nodes, cycle protection, and TREE profile extraction support | Independent algorithm claim |
| Context information | Extraction and communication of event stream, root node, and `tree:viewDescription` context; optional interpretation of retention policies and consumer-oriented context semantics | Independent algorithm claim |

LDES 1.0 defines two synchronization modes and does not require a client to
implement both, so the ordered and unordered claims are independent: an
ordered-only client is not required to pass the unordered group, and neither is
downgraded because of the other. Applicability follows the modes a scenario's
runs declare, not the group it reports into. Obligations shared by both modes -
HTTP behavior, discovery, state and deduplication - therefore have a fixture in
each mode, so a client that declares only one mode can still demonstrate them.
Scenarios requiring a mode a client does not declare are `earl:inapplicable`.

`MUST` failures affect the relevant group and CI exit status. `SHOULD`
failures are reported as advisory assertions; they remain visible in EARL,
JSON, and HTML evidence but do not make the main compliance group fail.
Optional capabilities, such as specialized TREE profile processing or deeper
retention-policy interpretation, produce named subclaims instead of silently
changing the baseline score.

An unsupported mode is `earl:inapplicable`, an unimplemented test is
`earl:untested`, and an inconclusive execution is `earl:cantTell`. None of
these is silently converted into a pass.

## How the suite works

```text
test manifest ─┬─> deterministic HTTP fixture server ─> client under test
               │                                      │
               └─> oracle <─ request log + events <─ adapter
                              │
                              └─> JSON summary + EARL report
```

Each atomic test directory contains:

- `manifest.ttl`: stable test identity, specification citation, requirement
  level, compliance group, and expected outcome;
- `scenario.yaml`: HTTP resources and response changes across synchronization
  runs. Routes match path *and* query string. A route may select a response by
  request header (`whenHeaders`) as well as by attempt number, and may split a
  body into delayed `chunks` so a fixture can observe behavior while a response
  is still being written. See `schemas/scenario.schema.json`.
- `responses/`: RDF representations and other response bodies;
- `expected/`: what the oracle checks.

Files under `expected/` are optional except `events.ndjson`:

| File | Checks |
| --- | --- |
| `events.ndjson` | The observable event trace. Member order is unconstrained within a contiguous block of same-run members in unordered mode; in ordered mode order is exact unless members share a `tieGroup`, which marks a legal ordering tie. A `dateTime` list asserts that a field holds a parseable timestamp without pinning its value. |
| `*.nq` | Member or context datasets, compared as RDF datasets: quads are deduplicated and blank nodes are matched by isomorphism, so serialization differences and blank-node labels do not matter. |
| `requests.json` | Request expectations per path and status: counts, exact `headers`, `headerIncludes`, `absentHeaders`, and `presentHeaders` for obligations that only require a header to be present. |
| `timing.json` | `minSpanMs` across requests to a path, and `minGapMs` between each consecutive pair. `minGapMs` observes that retries are spaced without prescribing a retry count, a back-off curve, or jitter. |
| `event-timing.json` | Whether a member was emitted before or after a given response completed, for immediate-emission and late-description cases. |

The runner starts a local scenario server and gives its entry-point IRI to an
adapter. The adapter invokes the real client and emits newline-delimited JSON
events. The oracle can inspect:

- emitted member identifiers and RDF datasets;
- order and duplicate emission;
- run completion, errors, context, and statistics;
- HTTP request headers, redirects, retries, timing, and node visits;
- behavior after a controlled restart with the same state directory.

The server, runner, and oracle must use virtual or bounded time for polling and
back-off tests. Tests must not depend on public LDES instances or wall-clock
delays.

The suite is implemented as a Node/npm runner:

```sh
npm install
npm test
```

`npm run conformance:reference` compiles the TypeScript runner and runs the
scenario set against a small reference adapter. It writes JSON evidence, a
normative coverage report, and an EARL report under
`reports/reference/`. This adapter exists to validate the harness and fixtures;
it is not a conformance claim for any production client.

`npm run conformance:all` invokes all candidate adapter declarations. An
adapter whose native build or service runtime is absent produces explicit
`earl:cantTell` assertions with its setup diagnostic. To generate the
human-readable report after one or more runs:

```sh
npm run report
```

Open `site/1.0/index.html` to inspect the LDES-styled report. The root
`site/index.html` redirects to the latest 1.0 report. It links each assertion
to its JSON evidence, EARL Turtle, client revision, adapter
availability, and dereferenceable test case IRI under
`https://www.pieter.pm/ldes-client-conformance-test-suite/1.0#`.

See [the architecture](docs/architecture.md), [requirement inventory](docs/requirements.md),
[adapter contract](docs/adapter-contract.md), [client landscape](docs/client-landscape.md),
[CI reuse guide](docs/reusing-in-client-ci.md), and [test authoring guide](tests/README.md).

## Candidate client adapters

Each adapter is an independent process implementing `probe`, `run`, and
`reset`. Tests never contain client-specific branches.

| Client | Adapter | Runtime status |
| --- | --- | --- |
| [rdf-connect/ldes-client][rdf-connect-client] | Direct Node adapter around `replicateLDES`, RDF/JS member quads, and the native saved-state directory | Pinned build runs locally |
| [OpenLDES Linked Data Interactions][openldes-client] | Java host around `MemberSupplier`, SQLite-backed native state, and a bounded synchronization-run bridge | Shaded JAR builds and runs locally with Maven/JDK 21 |
| [europeana/rd-ldes-client][europeana-client] | Java host around `TraversalOrderedByTimestamp` and `ActivityHandler`, including native timestamp state | Shaded JAR builds and runs locally without the unavailable upstream demo dependency |

Adapters live outside the normative test definitions. A defect in an adapter
must result in `earl:cantTell`, not `earl:failed`.

For example, to run the latest rdf-connect checkout:

```sh
git clone https://github.com/rdf-connect/ldes-client .clients/rdf-connect
npm --prefix .clients/rdf-connect ci
npm --prefix .clients/rdf-connect run build
npm run build
LDES_CT_RDF_CONNECT_ROOT="$PWD/.clients/rdf-connect" \
  node dist/cli.js run --adapter rdf-connect --tests tests \
  --out reports/rdf-connect --no-fail
npm run report
```

The Java host build entry points are
`adapters/openldes-ldi/build.sh` and `adapters/europeana/build.sh`.

## Continuous publication

[The conformance workflow](.github/workflows/conformance-pages.yml) checks out
the latest default-branch head of the three clients, builds the available native hosts, runs the
same black-box suite in isolated matrix jobs, combines their EARL/JSON
artifacts, and deploys the HTML report with GitHub Pages.

The repository must have **Settings → Pages → Build and deployment → Source**
set to **GitHub Actions**. Test failures are published as results and therefore
do not fail the workflow; runner/build problems remain `cantTell` with a
diagnostic. The workflow runs daily, but a client is only built and tested again when
its default branch head or this suite changed; otherwise its cached report for
that (client revision, suite commit) pair is republished. The EARL report and
HTML page record the exact client revision that was tested.

## Design principles

1. **Specification first.** Test IDs are assigned to clauses, not inherited
   from one client's feature names.
2. **One reason to fail.** Atomic tests isolate a behavior where practical.
3. **Protocol realism.** Fixtures are valid HTTP and RDF; malformed inputs are
   only used when a requirement defines error behavior.
4. **Representation independence.** RDF datasets are compared semantically
   with blank-node-aware dataset isomorphism, not as text.
5. **Observable evidence.** Every assertion retains enough evidence to explain
   the outcome without client source access.
6. **Versioned claims.** Reports identify the client build, adapter, suite
   revision, mode, platform, and execution time.
7. **No implementation favoritism.** Test fixtures are not copied unchanged
   from one candidate client's own tests.

## Status and next steps

The runner, request/event/RDF-isomorphism oracles, EARL/JSON/HTML reports,
